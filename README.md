# FitBooking Frontend

## Overview

This folder contains the frontend foundation for the FitBooking personal-training booking platform. It uses:

- Next.js 14 App Router
- React 18
- TypeScript
- Tailwind CSS
- lucide-react

The app combines a responsive member experience with a FastAPI backend. Member sign-in, profile, catalog, booking, package, and payment-history flows use the API when configured; trainer/admin areas and some secondary screens still include preview data. Booking checkout uses a one-click simulated payment only: it updates demo order state and never contacts a payment gateway or transfers money.

## UI prototype

### Pages and demo accounts

- `/` — Landing page with sign-in and account-creation entry points
- `/signin` and `/signup` — Separate sign-in and member registration pages
- `/member` — Member workspace to explore trainers, book sessions, view packages, leave reviews, and track progress
- `/trainer` — Schedule, member, and member-trainer messaging workspace
- `/admin` — Overview of members, trainers, bookings, packages, and workflows

Demo accounts:

| Member | `alex.demo` | `DemoPass123!` |
| Trainer | `tan.coach` | `DemoPass123!` |

Members can register additional accounts. When the API is online, authentication and supported member data are stored by the backend; when using local preview mode, demo state may be kept in the current browser's `localStorage`. Demo credentials and preview role checks are for development only and must not be used as production security controls.

### Prototype screens

The member workspace includes:

1. Welcome page and member dashboard
2. Trainer discovery and trainer profiles
3. Courses and booking
4. Checkout and booking confirmation (no real payment is processed)
5. Bookings, package list, and package details
6. Reviews, progress, and member profile/settings
7. Messaging with a trainer

Trainer and admin workspaces share the member experience's visual theme but have role-specific navigation and layouts. Some schedule, chat, admin, and workflow views still use sample data. Checkout's **Simulate payment** action is the only payment path in this UI; it confirms a demo booking/order and does not process a real payment.


To connect the frontend to FastAPI, copy `.env.example` to `.env.local`:

```bash
NEXT_PUBLIC_API_BASE_URL=http://localhost:8000
```

The API client normalizes this value to the `/api/v1` base path. With the backend running, member checkout creates a booking and calls `POST /api/v1/orders/bookings/{booking_id}/mock-pay` after the user clicks **Simulate payment**. This endpoint is for local/demo testing only and does not integrate with a payment processor.

## Field naming rules

`lib/database.ts` uses `snake_case` field names to match the MySQL tables exactly, for example:

- `user_id`
- `coach_id`
- `booking_id`
- `booking_date`
- `start_time`
- `duration_minutes`
- `service_mode`
- `payment_status`
- `remaining_sessions`

Do not convert fields in the primary types to camelCase; the names must remain aligned with the backend and SQL schema.

## Enums and validation

The frontend must use enum values that match the database exactly:

- `users.role`: `MEMBER`, `COACH`, `ADMIN`
- `users.status`: `ACTIVE`, `DISABLED`
- `coach.coach_level`: `BEGINNER`, `INTERMEDIATE`, `ADVANCED`, `MASTER`
- `coach.service_mode`: `GYM`, `HOME`, `BOTH`
- `booking.service_mode`: `GYM`, `HOME`
- `booking.status`: `PENDING`, `CONFIRMED`, `CANCELLED`, `COMPLETED`, `NO_SHOW`
- `orders.payment_status`: `UNPAID`, `PAID`, `CANCELLED`, `REFUNDED`
- `member_package.package_type`: `5+1`, `10+3`, `20+7`
- `member_package.status`: `ACTIVE`, `EXHAUSTED`, `EXPIRED`, `CANCELLED`
- Dynamic schedule `status`: `AVAILABLE`, `BOOKED`, `BREAK`, `BLOCKED`

Important constraints:

- `coach_no` must contain 4–8 digits.
- `start_time` must align to a 10-minute interval.
- `duration_minutes` must be divisible by 10.
- `break_minutes` must be `10`, `20`, or `30`.
- `service_mode = GYM` requires `gym_id` and no `service_address`.
- `service_mode = HOME` requires `service_district` and `service_address`, and no `gym_id`.
- Never display `password_hash` in the UI.
- Prices are in THB and should be displayed with two decimal places.

## Backend integration

The shared API client in `lib/api-client.ts` calls FastAPI and checks HTTP/API errors before exposing data to the UI. A typical request looks like:

```ts
const response = await fetch(`${process.env.NEXT_PUBLIC_API_BASE_URL}/api/bookings`);

if (!response.ok) {
  throw new Error("Unable to load bookings.");
}

const bookings: Booking[] = await response.json();
```

FastAPI returns JSON using the SQL column names directly, for example:

```json
{
  "booking_id": 2401,
  "member_id": 31,
  "coach_id": 1,
  "course_id": 1,
  "gym_id": 1,
  "package_id": null,
  "booking_date": "2026-10-13",
  "start_time": "09:00:00",
  "end_time": "10:00:00",
  "duration_minutes": 60,
  "break_minutes": 10,
  "service_mode": "GYM",
  "service_district": null,
  "service_address": null,
  "price": 1200,
  "status": "CONFIRMED"
}
```

## Dynamic schedule tables

The frontend must not accept or construct dynamic table names:

```text
coach_schedule_<coach_no>
```

Send only the `coach_id` or the requested booking time range to FastAPI. The backend is responsible for looking up `coach_no`, validating its format, and safely creating or selecting the table.
